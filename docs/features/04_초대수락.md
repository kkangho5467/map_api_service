# 04. 초대 수락 · 실시간 알림

> 완성일: 2026-09-28 · 관련 파일: `supabase/04_couple_requests.sql`, `supabase/05_realtime_couple.sql`,
> `src/hooks/useProfile.js`, `src/components/CoupleCard.jsx`, `TabBar.jsx`, `src/App.jsx`

## 왜 만들었나
예전에는 초대 코드만 입력하면 **상대 동의 없이** 커플이 성립했습니다. 커플이 되면 찜·기록을 서로 볼 수 있으므로, 양쪽이 동의해야 연결되도록 바꿨습니다.

## 어떻게 동작하나
```
A: 코드 입력 → [요청] ──▶ couple_requests에 1행 (대기 중)
                           │  Realtime 알림
B: 🔴 빨간 점 + 💌 받은 요청 ◀┘
   ├ [수락] → couples + couple_members 생성, 요청 삭제 → A·B 모두 D+1 (A는 실시간 전환)
   └ [거절] → 요청 삭제 → A 화면이 조용히 입력칸으로 복귀
A: [취소] → 요청 삭제 → B의 받은 요청 사라짐
※ A와 B가 서로에게 요청하면 둘 다 동의한 것이므로 바로 연결
```
- 정한 정책: 취소 가능 · 만료 없음 · MY 탭 빨간 점 · 거절은 알리지 않음 · 보내는 요청은 1개만
- 요청 테이블에는 **대기 중인 요청만** 남습니다. 처리되면 지워서 상태 관리가 단순합니다.

## 핵심 개념
| 용어 | 쉬운 뜻 |
|---|---|
| RPC 함수 | 화면이 부르는 DB 함수. "내게 온 요청만 수락 가능" 같은 검사를 DB 안에서 함 |
| unique 제약 | `sender_id`에 걸어서 "한 사람당 보낸 요청 1개" 규칙을 DB가 지킴 |
| Supabase Realtime | DB가 바뀌면 서버가 앱에 즉시 알려 주는 기능 (구독 = "이 변화 생기면 알려줘") |
| 발행 목록(publication) | Realtime이 지켜보는 테이블 목록. 여기 없으면 구독해도 알림이 안 옴 |
| visibilitychange | 사용자가 다른 앱에 갔다가 돌아온 순간. 이때도 한 번 더 조회(안전망) |

## 막혔던 점 → 해결
- 새 요청이 새로고침해야 보임 → Realtime 발행 목록이 비어 있었음 → 두 테이블 추가 + 앱에서 구독
- 거절·취소가 상대 화면에서 안 사라짐 → DELETE 알림은 지워진 값이 비어서 옴(id 비교 실패) → "대기 중인 요청이 있을 때만" 다시 조회
- 카카오 계정이 1개 → Supabase에 테스트 계정을 만들고 SQL로 상대 동작을 흉내

## 보안 설계 포인트
- 테이블 직접 쓰기 금지, 검사가 들어 있는 함수로만 요청을 만들고 지움
- 예전 즉시 연결 함수(`connect_couple`)는 실행 권한을 막아 수락 단계를 건너뛸 수 없음
- Realtime 새 요청 알림은 RLS가 적용돼 **내 요청만** 전달됨

## 이렇게 설명하세요
> "커플 연결을 '요청 → 수락' 2단계로 바꿔 양쪽이 동의해야만 연결되게 했습니다. 요청·수락·거절은 DB 함수 안에서 본인 확인을 거치고, 테이블 직접 수정은 막아 조작을 차단했습니다. Supabase Realtime을 적용해 상대가 요청하거나 수락하면 새로고침 없이 바로 화면에 반영됩니다."

## 남은 한계

- 초대 링크 공유 방식은 보류 (필요하면 화면만 추가로 가능)
