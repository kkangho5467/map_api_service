# Pop-Pin 프로젝트 스킬 안내서 (초보자용)

> 이 문서는 우리 프로젝트(`.claude/skills/`)에 직접 추가한 스킬 5개와,
> 함께 쓰는 **플러그인 스킬 1개(Karpathy)** · **MCP 도구 2개(Playwright, Context7)** 를 쉽게 설명합니다.
> 전체 스킬이 어디에 있고 어떤 역할인지는 [SKILLS_MAP.md](SKILLS_MAP.md)를 보세요.
> 최종 갱신: 2026-09-28

---

## 먼저 구분하기: 스킬 · 플러그인 · MCP

셋 다 "Claude를 더 똑똑하게 만드는 것"이라 헷갈리기 쉬워요.

| 구분 | 정체 | 비유 | 우리 프로젝트 예시 |
|---|---|---|---|
| **스킬** | `SKILL.md` 매뉴얼 파일 (글만 있음) | 📘 업무 매뉴얼 | `supabase-migration`, `verify-app` … |
| **플러그인** | 스킬·명령어 등을 묶어 설치하는 **포장 상자** | 📦 매뉴얼 묶음 택배 | Karpathy Skills (안에 스킬 1개) |
| **MCP** | 외부 프로그램·서비스에 **실제로 접속**하는 연결 통로 | 🔑 출입증 + 도구 | Playwright, Context7, Supabase |

- **스킬은 "어떻게 할지"를 알려주고, MCP는 "실제로 할 수 있게" 해줍니다.**
- 예: `verify-app` 스킬(매뉴얼)에 "모바일 화면을 캡처해라"라고 적혀 있어도, 실제로 브라우저를 여는 건 Playwright MCP(도구)입니다.
- 그래서 Karpathy Skills는 **스킬이 맞고**(플러그인으로 설치), Playwright·Context7은 **스킬이 아니라 MCP**입니다.

---

## 스킬이 뭔가요?

**스킬 = Claude에게 주는 "업무 매뉴얼"** 입니다.

- 신입 직원에게 "DB 바꿀 땐 이 체크리스트대로 해"라고 매뉴얼을 주는 것과 같아요.
- 각 스킬은 `SKILL.md` 파일 하나이고, 맨 위에 **언제 쓰는지(description)** 가 적혀 있어요.
- Claude는 대화 내용이 description과 맞으면 **알아서 매뉴얼을 펼쳐 보고** 그대로 작업합니다.
- 직접 부르고 싶으면 채팅창에 `/스킬이름` 을 입력하면 됩니다. (예: `/verify-app`)

```
사용자 요청 ──▶ Claude가 description 비교 ──▶ 맞는 스킬의 SKILL.md 읽기 ──▶ 규칙대로 작업
```

### 왜 스킬을 쓰나요?

| 스킬이 없을 때                                           | 스킬이 있을 때                               |
| -------------------------------------------------------- | -------------------------------------------- |
| 채팅마다 "RLS 꼭 켜줘", "5173 포트 확인해줘"를 반복 설명 | 한 번 적어두면 매번 같은 기준으로 작업       |
| 새 채팅에서 규칙을 잊어버림                              | 파일로 저장돼 있어 새 채팅에서도 그대로 적용 |
| 사람마다·날마다 품질이 들쭉날쭉                         | 체크리스트로 빠뜨리는 것 방지                |

## 우리 프로젝트 스킬 5개

### 0. `feature-kickoff` — 기능 시작 도우미 🚀

**한 줄 요약:** "○○ 만들자" 한 줄만 말하면, Claude가 **정할 것을 선택지로 묻고 계획을 세워** 진행.

**언제 쓰이나요?**

- "초대 수락 만들자", "찜 기능 구현하자", "다음 작업 진행하자"

**어떻게 진행되나요?**

1. 진행 기록과 관련 코드를 확인
2. 사용자가 정해야 할 **정책만** 선택지 버튼으로 한 번에 질문 (추천안이 맨 위, 모르겠으면 추천 클릭)
3. 단계별 계획 + **각 단계에 쓸 스킬·MCP와 이유**를 보여줌
4. SQL이 있으면 작성 후 멈춤 → 사용자가 실행하고 "실행 완료" → 화면 작업
5. 끝나면 보안 점검 → 진행 기록 → **기능 설명 노트** 작성

**비유:** 인테리어 상담사. "원하는 느낌만 골라 주세요, 공정표는 제가 짤게요"

---


### 1. `supabase-migration` — DB 설계도 작성 매뉴얼 🗄️

**한 줄 요약:** Supabase 테이블·보안 정책을 **안전한 SQL 파일**로 만드는 규칙.

**언제 쓰이나요?**

- "찜(likes) 테이블 만들어줘", "코스 저장 기능 DB 추가해줘"처럼 DB 구조를 바꿀 때

**무엇을 지켜주나요?**

- 📁 `supabase/NN_설명.sql`처럼 **번호를 붙인 새 파일**로 작성 (기존 파일은 수정 금지 → 이력이 남음)
- 🔁 **여러 번 실행해도 안전하게** (`if not exists` 등) → 실수로 두 번 Run해도 에러 없음
- 🔒 **RLS(행 단위 보안)** 필수 → "내 데이터는 나와 연인만 볼 수 있게"
- 🧩 커플 데이터는 기존 함수 `my_couple_id()` 재사용 → 무한 재귀 에러 예방

**비유:** 건물 증축할 때 "기존 설계도는 건드리지 말고, 증축 도면을 새로 그려서 보안 점검 도장까지 받아라"

---

### 2. `security-checklist` — 커밋 전 보안 점검표 🛡️

**한 줄 요약:** 코드를 올리기 전 **비밀 키 노출·해킹 위험**을 점검하는 체크리스트.

**언제 쓰이나요?**

- "보안 점검해줘", "커밋 전 확인", "배포해도 돼?"
- 로그인·DB·API 키를 다루는 코드를 고친 직후

**무엇을 점검하나요?**

1. **비밀 키 노출** — `VITE_`가 붙은 값은 브라우저에 공개됨! 비밀 키에는 절대 붙이지 않기
2. **XSS(스크립트 주입)** — 사용자 입력을 `innerHTML`에 넣지 않기
3. **Supabase** — 새 테이블에 RLS가 켜졌는지
4. **에러 처리** — 실패 시 사용자에게 한글 안내가 뜨는지
5. **인증 흐름** — 로그아웃 상태에서 로그인 전용 기능이 불리지 않는지

**비유:** 집을 나서기 전 "가스 잠갔나? 문 잠갔나?" 확인하는 체크리스트

---

### 3. `verify-app` — 실제 동작 확인 절차 🔍

**한 줄 요약:** 코드를 고친 뒤 **진짜로 잘 되는지** 빌드·화면으로 확인하는 절차.

**언제 쓰이나요?**

- "확인해줘", "화면 봐줘", "잘 되는지 테스트해줘"
- 화면이나 기능을 수정한 뒤

**어떤 순서로 확인하나요?**

1. **빌드 확인** — 에러 없이 빌드되는지 (실패하면 "완료"라고 말하지 않음)
2. **포트 확인** — 개발 서버가 꼭 `5173`번이어야 함 (다르면 카카오 로그인 후 배포 주소로 튕김)
3. **화면 확인** — 모바일 크기(390×844)로 접속해 스크린샷, 콘솔 에러 확인
4. **로그인 화면은 사용자가 직접** — 카카오 계정은 자동 입력하지 않음

**비유:** 요리 후 "맛보기" 단계. 레시피대로 했다고 끝이 아니라 직접 먹어보고 확인

---

### 4. `progress-log` — 작업 일지 작성 규칙 📒

**한 줄 요약:** `PROGRESS_LOG.md`에 **무엇을 했고 다음에 뭘 할지** 정해진 형식으로 기록.

**언제 쓰이나요?**

- "기록해줘", "진행 사항 정리", "여기까지 저장"
- 새 채팅을 시작해 "다음에 뭐 하지?"를 정할 때

**어떻게 기록하나요?**

- `완료한 작업`은 날짜별로 **추가만** (과거 기록은 수정 금지)
- `다음 작업`은 끝난 항목을 지우고 최신 상태 유지
- 비밀번호·키 값은 **절대** 적지 않음
- `PROGRESS_LOG.md`는 `.gitignore` 대상 → 내 컴퓨터에만 저장됨

- 기능이 완성되면 `docs/features/NN_기능.md` **설명 노트**도 작성 (git에 올라감, 발표·면접용 "이렇게 설명하세요" 포함)

**비유:** 교대 근무자에게 남기는 인수인계 노트 + 기능별 "작품 설명서". 새 채팅(=다음 근무자)이 이걸 읽고 바로 이어서 일함

## 함께 쓰는 플러그인 스킬 1개

### 5. `karpathy-guidelines` (Karpathy Skills 플러그인) — 코딩 태도 가이드 🧭

**한 줄 요약:** AI가 자주 하는 코딩 실수를 줄이는 **4가지 원칙**.

**어디서 왔나요?** 사용자 전역 플러그인 → 내 PC의 **모든 프로젝트**에서 사용 (Pop-Pin 전용 아님)

**언제 쓰이나요?**

- 코드를 작성·리뷰·리팩터링할 때 자동으로 참고

**4가지 원칙**

1. **단순하게** — 요청하지 않은 기능·추상화를 덧붙이지 않기
2. **필요한 곳만 수정** — 관계없는 코드는 건드리지 않기 (수술하듯 정확하게)
3. **가정은 먼저 말하기** — 모르는 부분을 추측으로 채우지 않고 확인
4. **완료 기준을 확인 가능하게** — "빌드 통과", "화면에 ♡ 표시"처럼 검증할 수 있는 목표 정하기

**비유:** 선배 개발자의 "코딩할 때 이것만은 지켜" 포스트잇

## 함께 쓰는 MCP 도구 2개 (스킬 아님!)

> MCP는 `/mcp`로 연결 상태를 확인합니다. 두 도구 모두 **user 범위**라 모든 프로젝트에서 쓸 수 있어요.

### 🎭 Playwright MCP — 브라우저 조종 도구

**한 줄 요약:** Claude가 **실제 브라우저를 열어** 클릭·입력·스크린샷을 하는 도구.

**언제 쓰이나요?**

- `verify-app` 스킬이 화면 확인 단계에서 사용 (모바일 390×844 캡처, 콘솔 에러 확인)
- "♡ 버튼 눌러보고 찜 탭에 뜨는지 봐줘" 같은 클릭 테스트

**주의할 점**

- 카카오 로그인 화면은 **사용자가 직접** 로그인 (계정 정보를 자동 입력하지 않음)
- 개발 서버가 `5173` 포트에 떠 있어야 함

**비유:** 내 대신 앱을 눌러보는 테스터

### 📚 Context7 MCP — 최신 공식 문서 검색 도구

**한 줄 요약:** React·Supabase·카카오맵 등 라이브러리의 **최신 공식 문서**를 찾아보는 도구.

**언제 쓰이나요?**

- 라이브러리 사용법·설정·에러를 다룰 때 (예: "Supabase RLS 정책 문법", "React useEffect 정리 함수")
- AI의 기억(학습 데이터)이 오래됐을 수 있어서, 문서를 직접 확인해 **예전 방식 코드를 막아줌**

**비유:** 기억에 의존하지 않고 최신판 교과서를 펴보는 습관

## 스킬들은 이렇게 함께 움직여요

찜 기능을 만드는 경우를 예로 들면:

```
⓪ feature-kickoff     → "찜 만들자" → 정책 선택지 질문 → 계획
        ↓
① supabase-migration  → likes 테이블 SQL 작성 (RLS 포함)
   + Context7 (MCP)       Supabase 최신 문법 확인
   + Supabase (MCP)       기존 테이블과 충돌 없는지 조회
        ↓
② (코드 작성)          → 상세 모달 ♡ 버튼, 찜 탭
   + karpathy-guidelines  필요한 부분만 단순하게
        ↓
③ verify-app          → 빌드 + 화면 캡처로 동작 확인
   + Playwright (MCP)     실제 브라우저로 클릭·캡처
        ↓
④ security-checklist  → 키 노출·RLS·에러 처리 점검
        ↓
⑤ 사용자가 직접 커밋·푸시
        ↓
⑥ progress-log        → "찜 기능 완료" 기록 + docs/features/ 설명 노트
```

## 스킬을 고치거나 추가하려면?

- 파일 위치: `.claude/skills/<스킬이름>/SKILL.md`
- 맨 위 `description`이 **언제 쓸지 판단하는 기준**이라 가장 중요해요. 구체적인 상황과 말투("확인해줘" 등)를 적을수록 잘 호출됩니다.
- 새 스킬이 필요하면 "○○할 때 쓰는 스킬 만들어줘"라고 요청하면 됩니다.
- `.claude/` 폴더는 git에 올라가므로 다른 컴퓨터에서도 같은 스킬을 씁니다.
