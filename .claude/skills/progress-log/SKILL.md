# PROGRESS_LOG.md 기록 규칙

`PROGRESS_LOG.md`(프로젝트 루트, .gitignore 대상 = 로컬 전용)를 갱신한다. 비밀번호·키 값은 절대 적지 않는다.

## 섹션 구조 (순서 유지)
1. `# Pop-Pin (팝핀) 진행 기록` + `## 기록 기준일` (최종 갱신 날짜 업데이트)
2. `## 완료한 작업` — `### YYYY-MM-DD 주제` 단위로 **추가만** 한다(과거 기록 수정 금지)
   - 무엇을 했는지 / 실행한 SQL 파일 / 트러블슈팅(에러 코드 → 원인 → 해결)
3. `## 현재 웹사이트 기능` — 현재 동작하는 기능 목록으로 **덮어쓴다**
4. `## 현재 상태` — 브랜치, Supabase SQL 실행 순서, 커밋·푸시 안 된 변경
5. `## 다음 작업` — 번호 목록, 완료된 항목은 지운다
6. `## 범위 결정` — 사용자가 내린 방향 결정과 날짜 (제외: 팝업스토어, 도착 인증 등)
7. `## 공유 기능 도입 시 검토 사항` 등 설계 메모
8. `## 개선 예정 (알려진 한계)`
9. `## 주의사항` — 보안 관련

## 작성 원칙
- 날짜는 절대 날짜(YYYY-MM-DD)로 쓴다.
- 짧은 불릿 위주, 초보자가 나중에 읽어도 이해되게.
- 사용자가 확인했다고 말한 것만 "확인 완료"로 적는다.
- 방향이 바뀌면 Claude 메모리(`pop-pin-progress`)도 함께 갱신한다.

## 기능 설명 노트 (`docs/features/`) — 기능 하나가 완성됐을 때
`PROGRESS_LOG.md`는 내 컴퓨터용 인수인계 노트(git 제외)이고, 설명 노트는 **남에게 설명하는 용도**(git 포함)다.
- 파일: `docs/features/NN_기능이름.md` (NN = 다음 번호, 예: `04_초대수락.md`)
- 형식: `docs/features/README.md`의 템플릿 섹션을 그대로 따른다. README의 목차 표에도 한 줄 추가한다.
- 분량: 한 화면(약 60줄) 이내. 코드 전체를 붙이지 말고 핵심 파일 경로만 적는다.
- "사용한 도구"에는 실제로 쓴 스킬·MCP만 적고, **왜 썼는지**를 한 줄로 쓴다.
- "이렇게 설명하세요"는 사용자가 발표·면접에서 그대로 읽을 수 있는 3문장 이내로 쓴다. 전문용어는 한 번 풀어 준다.
- 버그 수정·문구 변경 같은 작은 작업은 노트를 새로 만들지 않고, 관련 노트의 "바뀐 이력"에 한 줄 추가한다.
