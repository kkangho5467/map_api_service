# 기능 시작 절차 (사용자는 고르기만, 계획은 Claude가)

사용자는 초보자라 긴 프롬프트를 쓰지 않는다. 짧은 요청만으로 필요한 결정을 **Claude가 먼저 끌어낸다.**

## 1. 맥락 파악 (조용히, 짧게)
- `PROGRESS_LOG.md`의 "다음 작업", "범위 결정", "개선 예정"에서 이 기능 관련 내용을 찾는다.
- 관련 SQL(`supabase/`)과 컴포넌트를 필요한 만큼만 읽는다. 전체 탐색 금지.
- 범위 결정에서 제외한 것(팝업스토어, 도착 인증)은 제안하지 않는다.

## 2. 정책 질문 — AskUserQuestion 1회로 끝낸다
- **사용자가 정해야 하는 것만** 묻는다: 서비스 규칙, 화면에서 보이는 동작, 범위(이번에 할지 나중에 할지)
  - 예: "보낸 요청을 취소할 수 있나요?", "알림을 어디서 보여줄까요?"
- **기술 선택은 묻지 않는다** (테이블 구조, 함수 이름, 라이브러리 등) → Claude가 관례대로 정하고 계획에 적는다.
- 질문 2~4개, 각 선택지 2~3개. 추천안을 맨 위에 두고 라벨 끝에 `(추천)`을 붙인다.
- 선택지 설명은 초보자 말투로, 결과가 어떻게 달라지는지 한 줄로 쓴다.
- 사용자가 요청에 이미 정한 내용은 다시 묻지 않는다. 물을 게 없으면 이 단계를 건너뛴다.

## 3. 계획 보여주기 (짧게)
아래 형식 그대로, 10~15줄 이내:

```
## ○○ 구현 계획
정한 정책: (선택 결과 한 줄 요약)

1. DB — supabase/NN_이름.sql        🧰 supabase-migration · 🔌 Supabase MCP(기존 구조 확인)
   → 사용자가 SQL Editor에서 실행 후 "실행 완료"라고 알려주기
2. 화면 — 수정할 파일 목록          🧰 karpathy-guidelines · 🔌 Context7(필요 시)
3. 확인 — 빌드 + 모바일 화면         🧰 verify-app · 🔌 Playwright
4. 마무리 — 보안 점검 · 기록 · 노트   🧰 security-checklist · progress-log

완료 기준: (확인 가능한 문장, 예: "요청 → 수락 후 두 계정 모두 D+1 표시")
```

- 각 스킬·MCP 옆에 **왜 쓰는지**가 드러나게 한다(사용자가 도구 역할을 배우는 목적).
- 계획을 보여준 뒤 바로 1단계를 시작한다. 별도 승인을 기다리지 않는다.

## 4. 단계별 진행
- DB가 있으면 **SQL 작성 후 멈춘다.** 사용자가 실행했다고 말하기 전에 화면 코드를 쓰지 않는다.
  (SQL이 실패하면 화면 코드를 다시 짜야 하므로)
- 에러가 나면 사용자에게 **에러 문구만** 붙여 달라고 요청한다.
- 각 단계 답변은 짧게: 무엇을 했는지 / 사용자가 할 일 / 다음 단계.

## 5. 끝나면
- `security-checklist`로 점검한다.
- `progress-log` 규칙으로 `PROGRESS_LOG.md`를 갱신하고 **기능 설명 노트**(`docs/features/`)를 작성한다.
- 커밋·푸시는 사용자가 직접 한다. 커밋 메시지 예시만 제안한다.
